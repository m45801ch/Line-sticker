# 動態貼圖打包規則設計

## 目標

動態貼圖（APNG）打包頁面需嚴格遵守 LINE 動態貼圖規格：檔案 ≤ 1MB、張數偶數且 ≤ 20、單次播放為整數秒。

## 背景

`src/components/ApngExporter.jsx` 已有 1MB 限制邏輯，但存在 bug：

- 編碼迴圈（159-168 行）嘗試 `[0, 256, 128]` 色彩，但終止條件 `attempt === 128` 永遠為真，導致超標檔案照樣送出。
- 下方的尺寸縮放 fallback（170-190 行）是死碼，永遠不會執行。
- 進入打包頁面（Step 4）無張數檢查。
- 每幀延遲使用 `Math.round`，可能使單次播放總毫秒 ≠ 整數秒（漂移）。

## 使用者決策

1. **優先降色彩/品質**：先逐步降低色彩數，全程保持原始尺寸（LINE 規格 320x270）。
2. **最後手段才縮小尺寸**：色彩降到最低仍超標時，才逐步縮小尺寸。
3. **保證輸出**：最終 Blob 必定 ≤ 1MB。
4. **張數檢查**：進入打包頁面前，去背後張數（未去背則用原始張數）須 ≤ 20，否則擋下並提醒。
5. **整數秒規則**：單次播放秒數必須為整數（1/2/3/4 秒），UI 不提供小數；實際播放毫秒總和必須精確等於 `秒數 × 1000`。

## 實作方案

### 色彩遞減

依序嘗試色彩數 `[256, 128, 96, 64, 48, 32, 16]`，第一個 ≤1MB 的結果即採用，維持原尺寸。

### 尺寸縮放（最後手段）

若 16 色仍超標，以 `scale = 0.8` 逐步縮小，並以最低色彩重編碼，直到 ≤1MB。下限設為 32px（避免退化到 0 尺寸的無窮迴圈），抵達下限仍超標時採用當下結果。

### 輸出資訊

打包完成後，於預覽區顯示實際使用的色彩數與最終尺寸，讓使用者知道壓縮程度。

### 進入打包頁面的張數檢查

在 `DynamicSticker.jsx` 的 stepper 點擊 Step 4（第 63 行）與 `BgRemover.jsx` 的「打包」按鈕（第 212 行）兩處入口檢查：

- 張數 = `processedFrames.length > 0 ? processedFrames.length : frames.length`
- 須 **≤ 20**
- 不符 → 不切換頁面，顯示提醒訊息（如「影格數需不超過 20 張，目前 X 張」）

### 整數秒與播放計算

- 秒數選項維持整數 `[1, 2, 3, 4]`，無小數輸入。
- 延遲計算：`base = floor(總毫秒 / 張數)`、`rem = 總毫秒 % 張數`；前 `rem` 幀為 `base + 1`ms、其餘 `base`ms。
- 總和 = `張數 × base + rem` = `秒數 × 1000` 精確成立，所有延遲皆為整數毫秒。

## 驗收標準

- 任一輸入在打包後下載的 APNG 檔案大小 ≤ 1MB（1024 × 1024 bytes）。
- 尺寸優先保持不變，僅在色彩降無效後才縮小。
- 介面顯示實際色彩數與最終尺寸。
- 去背後張數 > 20 時，無法進入打包頁面並顯示提醒。
- 單次播放總毫秒數精確等於 `秒數 × 1000`，無漂移、無小數。
